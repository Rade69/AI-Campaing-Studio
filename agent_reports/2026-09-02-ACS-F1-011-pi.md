## Implementation summary

### `select_allowed_facts.py`

`AllowedFactSet(fact_ids, selection_reasons)` + `select_allowed_facts`:
keeps only `is_fact_usable` facts, matches `facts_needed` phrases via
case-insensitive substring against `fact.content` and `fact.logical_fact_id`,
records the matching phrase as the selection reason. Empty `facts_needed` →
empty set (not an error).

### `claim_validator.py`

`validate_claim(claim, allowed, fact_repo) -> ContentClaim` (plan §35 only):
- `FACT`: must have ≥1 `fact_id`; each must exist (`get_fact`), be usable
  (`is_fact_usable`), and be in `allowed.fact_ids`. All pass →
  `VERIFIED_BY_FACT`; otherwise `UNSUPPORTED` with reason codes
  (`missing-fact-id`, `fact-not-found`, `fact-not-approved`, `fact-not-offered`).
- `CTA`/`OPINION`/`CREATIVE` → `NON_FACTUAL` always (no term-lists — A12).

### `generate_social_post.py`

`GenerateSocialPost(...).execute(campaign_id, plan_id, campaign_item_id, target)
-> ContentPiece`: load campaign/plan → find item in `plan.items` (in-memory,
no new repository method) → snapshot → facts → `select_allowed_facts` →
`post_generation/1` prompt → `AIRequest` (system=instructions, user=item +
brand summary + allowed-fact text + target) → AI call → `model_validate` →
`validate_claim` per claim → **interim status** (`UNSUPPORTED`→`NEEDS_REVIEW`,
else `GENERATING`, never `DRAFT`) → `SocialPostPayload` (`visual_direction`
None) → `ContentPiece` → `save_content_piece` inside `with uow: ... commit()`.

Depends only on ports + local `_UnitOfWork` protocol; no channels/ai_registry
imports.

## Design notes for review

1. `selection_reasons` is a plain `dict` per the contract (mutable field inside
   a frozen dataclass — contract-specified, not wrapped in `MappingProxyType`).
2. Added `fact-not-found` as a fourth reason code for a referenced fact that
   does not exist; the contract named `missing-fact-id`/`fact-not-approved`/
   `fact-not-offered` and left the not-found case to reason.
3. The integration end-to-end test builds the `CampaignPlan` directly (rather
   than going through `GenerateCampaignPlan`) because plan generation is
   already covered by ACS-F1-009; it still chains
   `LoadBrandFixture → CreateCampaign → (plan) → GenerateSocialPost` with a
   real FACT claim resolved from the real snapshot facts.
