## Implementation summary

### `RevisionType` (additive)

Added a 10-value `StrEnum` (`SHORTER`…`CUSTOM`) below `RevisionOrigin`.
`RevisionOrigin`/`Revision` untouched (diff shown below).

### `ReviseContentPiece`

`ReviseContentPiece(content_repo, fact_repo, revision_repo, prompt_repo,
ai_port, unit_of_work)` — note `revision_repo` is the sixth constructor
parameter (the contract's sketched signature omitted it; the contract body
explicitly instructs adding it).

`execute(content_piece_id, revision_type, instruction) -> ContentPiece`:
load piece (`None`→`EntityNotFound`) → reject missing payload →
reject `NEW_VISUAL_DIRECTION` before any AI call → `_ALLOWED_FIELDS` lookup →
load allowed-fact text → `revision/1` prompt → `AIRequest` (immutable fields
listed) → AI call → `RevisionOutput.model_validate` → **partial-field contract
check** (`changed_fields - allowed_fields` non-empty → `InvariantViolation`) →
apply only changed fields (skip explicit nulls; `hashtags` coerced to tuple) →
re-lint existing claims (not regenerated) → `derive_content_status` →
**APPROVED → always `NEEDS_REVIEW`** → compute next `version` from
`list_entity_revisions` → build `Revision` → persist revision + updated piece
atomically.

Reuses `lint_claim`/`load_claim_rules`/`derive_content_status` (no duplicated
logic). Depends only on ports + local `_UnitOfWork`.

## Design notes for review

1. `_apply_changes` skips an explicit `null` for a changed field (treated as
   "no change") and coerces `hashtags` `list -> tuple`; documented in its
   docstring. `type: ignore[arg-type]` on the `replace(**changes)` line is
   necessary because the field names come from the Pydantic `model_fields_set`.
2. Integration tests use a minimal FK chain
   (`LoadBrandFixture → CreateCampaign → APPROVED plan → hand-inserted
   ContentPiece`) rather than the full end-to-end chain including
   `ApproveCampaignPlan`/`GenerateSocialPost` — the contract allows the
   "minimal" integration form when full chain setup is too heavy.
