# Fix runda (2026-09-04) — BF-1: DeepSeek odbija `response_format: json_schema`

**Nalaz (Human Owner, živi poziv van formalnog review-a):** stvaran DeepSeek poziv
sa `response_format={"type": "json_schema", ...}` vraća:

```text
openai.BadRequestError: Error code: 400 - {'error': {'message': 'This
response_format type is unavailable now', 'type': 'invalid_request_error', ...}}
```

Moj prethodni `OUT_OF_SCOPE_FINDINGS: Nema` bio je tačan koliko je mock-ovan suite
mogao pokazati — fake klijent nikad ne validira da li backend STVARNO prihvata
`response_format`, samo da li kod ispravno GRADI zahtjev. Živ poziv (koji nijedan
korak nije radio, ni ja ni reviewer) je otkrio pravi incompatibility. Potvrđen fix
smjer (koordinator, živo testiran): DeepSeek prihvata stariji `json_object` mod,
gdje šema ide kao tekst u prompt + eksplicitna instrukcija o tačnom broju stavki.

## Šta je urađeno

1. `OpenAIAdapter` sada ima konstruktorski parametar
   `structured_output_mode: str = JSON_SCHEMA_MODE` (vrijednosti `"json_schema"`
   ili `"json_object"`; nepoznata vrijednost → `ValueError`).
   - `json_schema` (default, NEDIRNUT): `response_format={"type": "json_schema",
     "json_schema": {...}}` — postojeći OpenAI put, bez promjene ponašanja.
   - `json_object`: `response_format={"type": "json_object"}` + JSON schema
     embedovana u `system_text` + eksplicitna "exact count" instrukcija.
2. Exact-count instrukcija se gradi iz DVA izvora (deterministički, testabilno):
   - array polja u `json_schema` gdje je `minItems == maxItems`
     (→ "array field `<path>`: exactly N item(s)");
   - `*_count: N` polja u `user_text` (→ "`<name>` = N: odgovarajuća izlazna
     kolekcija mora imati tačno N stavki").
   Ovo pokriva i `content_piece_count` slučaj iz `GenerateCampaignPlan`
   (`user_text` ga sadrži; `items` array u `CampaignPlanOutput` schema-i NEMA
   `minItems`/`maxItems`, pa je text-detect nužan — sama array-detekcija ne bi
   uhvatila taj broj).
3. Fabrike u `openai_compatible_providers.py`:
   - `build_deepseek_adapter` → `structured_output_mode=JSON_OBJECT_MODE`
     (DeepSeek živo potvrđeno odbija `json_schema`).
   - `build_openrouter_adapter` → `JSON_OBJECT_MODE` (KONZERVATIVAN default —
     OpenRouter NIJE živo testiran, ne pretpostavljam da `json_schema` radi).
   - `build_openai_compatible_adapter` → default `JSON_OBJECT_MODE`, pozivalac
     može eksplicitno tražiti `JSON_SCHEMA_MODE` ako zna da njegov endpoint
     podržava.

# Fix runda 2 (2026-09-04) — R2-BF-1: exact-count regex hvata `discount`/`account_id`

**Nalaz (Codex re-review, nezavisno reprodukovan):** `_COUNT_LINE_RE` je hvatao BILO
KOJI identifier koji negdje sadrži podstring "count", ne samo stvarna `*_count` polja.
`discount: 20` i `account_id: 123` (plauzibilni marketing tekstovi) bi modelu dali
POGREŠNU hard instrukciju ("generiši tačno 20/123 stavke"). Realan prompt defekt u
`json_object` modu (baš tamo gdje schema nije server-side enforced).

## Fix — word-boundary regex, NE doslovan Codex-ov predlog

Codex-ov predlog (`(?:[A-Za-z][A-Za-z0-9_]*_count|count)`) JE MANJKAV za
`discount` — doslovno testirano prije primjene:

```text
$ python -c "..."
CASE: 'discount: 20'
  codex   : [('count', '20')]      <- i dalje false positive!
  boundary: []
```

Razlog: "discount" se ZAVRŠAVA sa "count" (dis+count), a unanchored `count`
alternativa u Codex-ovom regex-u matchuje taj podstring. Zato sam umjesto toga
koristio word-boundary verziju:

```python
r"(?P<name>(?:[A-Za-z][A-Za-z0-9_]*_count|\bcount\b))\s*:\s*(?P<value>\d+)"
```

`\bcount\b` znači "count kao cijela riječ", pa NE matchuje "count" unutar
"discount" (između 's' i 'c' nema word boundary) niti "account" u "account_id".
Verifikacija protiv svih slučajeva (doslovan output):

```text
CASE: 'content_piece_count: 3'  -> [('content_piece_count', '3')]
CASE: 'count: 3'                -> [('count', '3')]
CASE: 'discount: 20'            -> []
CASE: 'account_id: 123'         -> []
CASE: 'item_count: 5'           -> [('item_count', '5')]
```
