## Implementation summary

`LoadBrandFixture(brand_repo: BrandRepositoryPort, fact_repo: FactRepositoryPort,
unit_of_work: _UnitOfWork)` with `execute(fixture_path: Path) -> BrandSnapshot`:

1. Reads + validates the JSON via `BrandFixtureSchema.model_validate_json`
   (before any repository call — invalid fixtures leave repositories untouched).
2. Maps via the existing `map_brand_fixture` (no duplicated logic).
3. Persists brand → facts → snapshot inside `with unit_of_work:` and calls
   `unit_of_work.commit()` only after all saves succeed; any exception lets
   the unit-of-work `__exit__` roll back.

The use-case depends only on the repository ports plus a local duck-typed
`_UnitOfWork` `Protocol` (no `sqlite3`/`SqliteUnitOfWork`/SQLite-adapter
import) — `SqliteUnitOfWork` satisfies the protocol at runtime. The caller
guarantees all three are bound to the same connection.

Reuses `resources/fixtures/brightsmile.json` (no parallel fixture, per 0A.5).

---

## Design decision

- `_UnitOfWork` is a local `Protocol` in `load_brand_fixture.py` (declares
  `__enter__`/`__exit__`/`commit`). The contract's `__init__` example showed
  only the two repositories, but the atomicity requirement (steps 4–5) needs
  a transaction boundary, so I added the third parameter. The use-case still
  has no infrastructure import.
- Integration test file is named `test_load_brand_fixture_integration.py`
  (not `test_load_brand_fixture.py`) to avoid pytest rootdir basename
  collision with the unit test of the same name.
