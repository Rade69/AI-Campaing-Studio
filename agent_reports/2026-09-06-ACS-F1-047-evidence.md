### Objective #1 — `JobManager.update_progress`

`src/ai_campaign_studio/jobs/manager.py:106-156` (novi metod, aditivan):

```python
def update_progress(
    self, job_id, current, total, phase="", message=""
) -> None:
    """Update progress fields on a RUNNING job.

    Best-effort: silently no-ops on unknown / terminal / non-RUNNING
    jobs so a progress update that loses a race with the worker's
    ``_finish()`` (or with cancellation) can never raise into user
    code.
    """
    with self._lock:
        state = self._jobs.get(job_id)
        if state is None:
            return
        if state.status is not JobStatus.RUNNING:
            return
        self._jobs[job_id] = replace(state, ...)
    self._emit(JobEvent(job_id=job_id, event_type=JobEventType.PROGRESS, ...))
```

## Preostali rizici (iskreno)

1. **Puni unit suite traje 95s** (108 testova). To je zbog `_wait_for_job_terminal` polling-a (default 5s timeout × 4 usporena test scenarija). Integracijski testovi nisu pokrenuti (timeout 120s+). Validacija prije release-a treba pokrenuti `tests/integration/presentation_webview/bridge/test_campaign_bridge_end_to_end.py` sa pravim provider credentials.

2. **Closure `_find_current_job_id` koristi `job_manager._lock` direktno** (private API). Ako se JobManager-ov interni state promijeni u budućnosti (npr. preimenovanje `_lock` → `__lock`), ovo puca. Trade-off: izbjegavanje širenja JobManager javnog API-ja za F1-047-need. Dokumentovano u kodu kao "private API".

3. **App.js polling interval je 1200ms**. Ako je posao kratak (1-2 itema, < 1s ukupno), korisnik ne vidi progress — final toast se pojavi tek nakon prvog polling intervala. Razmatra se smanjenje na 500ms u budućem tasku ako korisnički test pokaže da je to vidljivo.

4. **Test cancel windowa (2.0s × 4 itema) je spor** — test traje ~7s. Razlog: moramo garantirati da `cancel_job` stigne TOKOM `generator.execute()` (ne prije, jer bi `raise_if_cancelled` već prošao na početku iteracije). Manji sleep-ovi su rizični za flakiness. Trade-off prihvaćen.
