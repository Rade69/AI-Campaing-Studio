## Implementation summary

### `get_brief()` — additive only

`CampaignRepositoryPort` gained exactly one method
`get_brief(brief_id: str) -> CampaignBrief | None`; the SQLite adapter got the
matching read + a `_brief_from_row` helper (deserializes `targets_json` and
`special_instructions_json`). No other method signature/behavior changed.
Diff is shown below in the report (3 lines added to the Protocol).

### `campaign_brief_mapper.py`

`map_campaign_brief(brief_input) -> CampaignBrief` — pure in-memory, `new_id()`
+ `utc_now()`, builds `CampaignTarget` objects from the validated input.

### `CreateCampaign`

`CreateCampaign(campaign_repo, unit_of_work)` with
`execute(brand_id, brand_snapshot_id, raw_brief) -> Campaign`:
validate (`CampaignBriefInput.model_validate`) → map → persist brief + DRAFT
campaign in one `unit_of_work` transaction.

### `GenerateCampaignPlan`

`GenerateCampaignPlan(campaign_repo, brand_repo, prompt_repo, ai_port,
unit_of_work)` with `execute(campaign_id) -> CampaignPlan`:
load campaign/snapshot/brief → `LEAD_GENERATION_V1` template →
`prompt_repo.get("campaign_plan","1")` → `AIRequest` (system = prompt
instructions, user = brief + snapshot summary + role list + template) →
`ai_port.generate` → `validate_campaign_plan_output` (schema + item count) →
deterministic domain validation → build `CampaignItem`s/`CampaignPlan` →
persist plan + `dataclasses.replace(campaign, status=PLAN_GENERATED)` in one
transaction.

**Domain validation (documented choice):** duplicate topics rejected; at least
2 distinct roles required when the plan has ≥ 2 items. All deterministic
Python — no LLM self-validation.

Both use-cases depend only on ports plus a local duck-typed `_UnitOfWork`
`Protocol` (no sqlite3/YAML/provider imports in `application/campaigns/`).
